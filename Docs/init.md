# Architecture Decision Record (ADR): Database Schema Design & Relational Persistence Model

## Status

Accepted

## Context

Our job aggregator application platform requires a highly structured, relational persistence model capable of storing upstream external entities alongside unique native elements. The system must distinctly handle external payloads (WeLoveDevs), internal postings (DevJobs), complex multi-role authorization records, operational tracking abstractions (such as job applications and favorites), and programmatic text enrichment blocks generated by our local AI pipeline.

Per the technical constraints, the database must enforce data integrity server-side, maintain relationships across restarts via persistent named volumes, and provide high-efficiency querying interfaces for our frontend list views.

## Decision

We choose to deploy a **MySQL/MariaDB Relational Database** structured around isolated data domains, automated enumeration checks, and optimized runtime abstractions (Views). This design strictly avoids mixing unvalidated JSON blobs with logical access layers and separates external transient records from moderated internal models.

---

## Why & Structural Evolution (Rationale)

### 1. Separation of External (`wld`) and Internal (`dj`) Infrastructures

* **Why:** External data from WeLoveDevs is read-only and mapped from an existing API schema, whereas native platform data requires distinct workflow flags like administration status hooks and structural software switches.
* **Control:** We enforce decoupled pairings for both companies and job lists (`companies_wld`/`jobs_wld` vs `companies_dj`/`jobs_dj`). This blocks downstream schema mapping side effects and allows on-demand external table flushes without threatening native datasets.

### 2. Native AI & Moderation Integration Columns

* **Why:** The project requires a text summarization capability and an explicit server-side authorization role boundary for moderators.
* **Control:** The `jobs_dj` table includes native fields for `ai_summary` (TEXT), `ai_tags` (JSON), and a status enumeration wrapper (`pending`, `approved`, `rejected`). This anchors advanced analytics and safety processing directly within the persistent state model.

### 3. State Interaction Engineering (`saved_jobs` & `applications`)

* **Why:** Candidates need a unified mechanism to interact across multiple job channels without database entry corruption.
* **Control:** Interaction data models run strict `ON DELETE CASCADE` foreign keys connected directly to primary account IDs. They use compound `UNIQUE KEY` configurations (`unique_saved` and `unique_application`) to prevent redundant candidate registrations.

### 4. Query Simplification via Unified Database Views (`unified_jobs`)

* **Why:** Complex backend endpoints requiring multi-table lookup algorithms generate high latency if handled through fragmented server-side operations.
* **Control:** We abstract database query tracking into a server-side relational view layer (`unified_jobs`). This uses a high-performance database-driven `UNION ALL` mechanism, automatically normalizing locations, companies, and visibility limits before feeding data to the backend API.

### Advanced Operations: Database View Definition

```sql
CREATE OR REPLACE VIEW unified_jobs AS
SELECT
    j.id, j.company_id, c.name AS company_name, c.sector AS company_sector,
    j.title, j.description, j.salary_min, j.salary_max, j.currency,
    j.contract_type, j.experience_years, j.remote_type, j.location, j.skills,
    j.created_at, 'wld' AS source, 'approved' AS status 
FROM jobs_wld j
LEFT JOIN companies_wld c ON j.company_id = c.id
UNION ALL
SELECT
    j.id, j.company_id, c.name AS company_name, c.sector AS company_sector,
    j.title, j.description, j.salary_min, j.salary_max, j.currency,
    j.contract_type, j.experience_years, j.remote_type, j.location, j.skills,
    j.created_at, 'dj' AS source, j.status
FROM jobs_dj j
LEFT JOIN companies_dj c ON j.company_id = c.id
WHERE j.is_deleted = FALSE;

```

## Trade-offs

### Pros

* **Logical Database Separation:** Structural modifications targeting native postings will never accidentally break external fields populated by the automated ingestion pipeline.
* **Soft Delete Capability (`is_deleted`):** Using an internal conditional boolean mapping prevents permanent operational data loss. Deleted jobs remain available for internal reporting metrics while instantly hiding from candidates via the `unified_jobs` view layer.
* **Unified API Query Contract:** The backend interface targets the single `unified_jobs` interface table, reducing standard routing parameters to basic database filters instead of relying on slow in-memory filtering loops.

### Cons & Limitations

* **Double Entity Constraints:** Storing separated structures for entities (`companies_wld` / `companies_dj`) forces the platform to manage dual lookup calls if a corporate entity operates inside both pipelines simultaneously.
* **Cross-Source Foreign Key Limitations:** Due to structural source encapsulation, the interaction tables (`saved_jobs`/`applications`) use logical bindings via `job_id` paired with `job_source` configurations rather than strict, standard database engine-enforced foreign keys on specific listing rows.

---

## Rejected Alternatives

### Alternative 1: Single Unified Jobs Table (Rejected)

* **Why Rejected:** Putting both internal and external data into one large table creates an unstructured data model. We would have to make mandatory fields like `ai_summary` or `status` nullable for external listings that don't use them. This approach degrades data integrity constraints and increases index fragmentation.

### Alternative 2: Total JSON Database Structure (Rejected)

* **Why Rejected:** Document databases are highly performant for streaming unstructured logs, but they introduce heavy computational complexity when computing aggregated statistics (such as computing minimum salary averages or matching candidate profile locations). Enforcing rigid schema types ensures data reliability throughout the application lifecyle.
